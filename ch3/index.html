Application processes

Network applications communicate as process pairs

Process means a running program. In networking, we describe communication as one process exchanging messages with another process on a different host.

1
Application layer ideaThe protocol defines message format and rules, such as HTTP request/response.
2
Real endpointThe endpoint is a running process, such as a browser process or web server process.
3
Client and server rolesThe client process starts the communication. The server process waits and responds.
Teach here: process pairs explain who communicates at the Application Layer.
Key transition
application softwarerunning processapplication protocol messagesnetwork delivery underneath
Socket API

Socket is the boundary between Application and Transport

A socket is not an application-layer protocol. It is the programming interface that a process uses to send data to, and receive data from, TCP or UDP.

1
Application processCreates application messages, such as HTTP GET or SMTP MAIL FROM.
2
Socket APIThe process calls the socket to pass bytes to TCP/UDP.
3
Transport layerTCP/UDP adds port numbers and delivers to the correct process.
Best sentence for students: Application writes messages; socket hands them to TCP/UDP.
Correct placement
Application LayerSocket API boundaryTransport LayerTCP / UDP

HTTP state behavior

State vs Stateless HTTP: how websites remember users

StateRemembered context such as login, cart, preferences, or API identity.
Stateless HTTPHTTP does not automatically remember a previous request.
Web apps add stateCookies, sessions, bearer tokens, and cache validators help the next request carry context.

Stateless HTTP

Read this story from top to bottom. The second request is treated like a new request unless it sends extra information.

Request 1GET /profileServer replies: 200 OK
↓
Request 2GET /cartNo cookie or token → server cannot automatically know who the user is
Key idea: HTTP request–response still works, but the protocol itself has no built-in memory of earlier requests.

HTTP evolution

HTTP version transition: 0.9 → 1.0 → 1.1 → 2 → 3

HTTP/0.9very early web
  • Only GET request
  • No headers
  • Mainly plain HTML documents
  • Very simple request/response
HTTP/1.0basic standard
  • Headers added
  • More methods: GET, POST, HEAD
  • Content types and status codes
  • Usually non-persistent
HTTP/1.1major improvement
  • Persistent connections by default
  • Required Host header
  • Better caching and chunked transfer
  • Foundation of the modern web
HTTP/2performance focus
  • Binary framing
  • Multiplexing many streams in one connection
  • Header compression
  • Faster page loading
HTTP/3modern transport
  • Runs over QUIC on UDP
  • Lower latency connection setup
  • Better loss recovery
  • Reduces transport head-of-line blocking
→more features
→better reuse
→more concurrency
→lower latency
Transition idea
simple text webpersistent HTTPmultiplexed streamsQUIC-based HTTP/3

What changed across versions?

The main transition is from simple single-object delivery to efficient multi-object delivery. Newer versions try to reduce delay, reuse connections better, and support modern web pages with many objects.

1.0new TCP connection often needed
1.1keep one connection alive
2many streams share one connection
3QUIC improves speed and recovery

Good teaching summary

HTTP/1.0 → HTTP/1.1Focus on connection reuse and better support for real websites.
HTTP/1.1 → HTTP/2Focus on sending many page objects efficiently through one connection.
HTTP/2 → HTTP/3Focus on transport improvement by moving from TCP to QUIC over UDP.
Important noteStudents should understand that the application-layer idea remains request–response, but the underlying efficiency mechanisms improve over time.

Email services

Email flow: simple and correct

1

Sender MUA

The sender writes the email in a mail app.

Message includes headers, body, and attachments.
2

SMTP submission

The mail app sends the message to the sender mail server.

Commonly SMTP submission on port 587.
3

DNS MX lookup

The sender server asks DNS which mail server handles the receiver domain.

DNS helps find the destination server; it does not carry the email body.
4

Receiver mail server

The sender server relays the email to the receiver server, which stores it in the mailbox.

Server-to-server delivery commonly uses SMTP.
5

Receiver MUA

The receiver reads or syncs the mailbox using IMAP or POP3.

IMAP syncs with the server; POP3 usually downloads mail.

Where DNS fitsDNS MX is only a helper step to find the receiver mail server.

SMTP submission: client to sender server
SMTP relay: sender server to receiver server
IMAP / POP3: receiver reads mailbox

Other Application-Layer Protocols

Many network services have their own message rules

DHCP

Automatically gives hosts IP settings such as IP address, subnet mask, gateway, and DNS server.

SSH

Provides secure remote login and command execution on another machine.

SNMP

Helps monitor and manage network devices such as routers, switches, and servers.

NTP

Synchronizes time between devices so logs and services use consistent time.

MQTT

Lightweight publish/subscribe messaging commonly used in IoT systems.

Telnet

Older remote login protocol; useful historically but not secure for modern use.

Lab Practice • 5–10 minutes

Lab: Why HTTP Is Insecure

Capture a simple HTTP login request and observe whether username/password data is readable in plaintext.

🎯 Lab goal

Students compare HTTP plaintext with HTTPS encryption by looking at a real HTTP request in Wireshark.

Use only dummy data. Never type a real username or password.

🌐 Public HTTP test site

Open this exact URL:

http://http-login.badssl.com/

Check the address bar still starts with http:// and shows “Not secure”.

🧪 Steps

1Open Wireshark and start capture on Wi‑Fi/LAN
2Use display filter: http
3Open http://http-login.badssl.com/
4Enter dummy data: student01 / test123
5Find the HTTP POST request → Follow TCP Stream

🔍 What students should see

The submitted form data may appear in readable text, such as:

username=student01&password=test123
